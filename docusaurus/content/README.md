# The documentation source

Everything Docusaurus reads is **generated** from this directory. This is the only place to edit.

```
docusaurus/
  content/docs/          ← the source. Edit here.
    11.13.0/             complete tree, frozen
    11.14.0/             only what differs from 11.13.0
    next/                work in progress (empty right now, so it serves 11.14.0)

  docs/                  ← generated. Gitignored. Do not edit.
  versioned_docs/        ← generated. Gitignored. Do not edit.
  versioned_sidebars/    ← generated. Gitignored. Do not edit.
  versions.json          ← generated. Gitignored. Do not edit.
  .docs-overlay/         ← generated. Gitignored. Holds the current version's tree and the manifest.
```

If you have worked on this site before, the muscle memory to unlearn is editing `docs/`. That directory
is now build output: an edit there survives until the next build and then disappears without a trace.
`npm run verify` catches it, and CI runs that on every merge request touching `docusaurus/`.

## Why it works this way

Each version folder holds **only what changed**. `11.13.0` carries the complete tree; `11.14.0` carries
its 119 overrides, 57 additions and 9 directives; `next` is empty and therefore serves exactly what
11.14.0 serves. Everything else is inherited.

That is what makes cutting a release free — `npm run cut 11.15.0` renames a folder, and git records a
rename with no content diff — and it is what stopped the version served at the site root from silently
falling three months behind `docs/`, which is why this migration happened.

Docusaurus cannot do this itself. It allows exactly one configurable source directory (the current
version's), `versioned_docs/version-X/` and friends live at fixed paths, and the docs plugin reads its
version metadata inside its own factory, before any plugin hook could intervene. So the tree it insists on
reading is written before the build instead.

## Editing

Everything is expressed **in the version that introduces it**, so a published version folder is never
reopened.

| To do this | Write this |
|---|---|
| add a page | the file, in the version that adds it |
| change a page | the file, in the version that changes it — older versions keep theirs, newer ones inherit yours |
| rename a page | `overlay: { renamedFrom: old/slug }` in the **new** file's frontmatter |
| delete a page | a file at the old path carrying `overlay: { deleted: true }` |
| point a deleted page somewhere | add `replacedBy: some/slug` beside `deleted` |

```yaml
---
title: Filters
overlay:
  renamedFrom: mint/configurations/filters
---
```

Two things worth knowing before you write a directive:

- **`renamedFrom`, `aliases` and `replacedBy` take slugs, not doc ids.** They coincide for most pages,
  but not for an index page: `mint/how-to/index.md` has the doc id `mint/how-to/index` and the slug
  `mint/how-to`. Naming the doc id points at a URL that does not exist; `npm run check` says so.
- **A page can only be inherited if no newer version has its own copy.** If you edit a file in
  `11.13.0`, every later version that does not override it changes too. `npm run check` lists what a
  version serves by inheritance.

### Navigation

Each version has its own `sidebars.json` at its root, inherited like anything else — a version that did
not change its navigation ships none. `11.13.0` and `11.14.0` each have one, because their sidebars
genuinely differ: `11.13.0` lists `atomic/changelog`, which `11.14.0` removes.

An inherited sidebar is **pruned** to what the browsing version actually serves: a reference to a removed
doc is dropped, a reference to a renamed one is rewritten, and an `autogenerated` block whose directory is
empty here is removed. Nothing is ever added — the categories are `autogenerated`, so a new page appears
by itself, whereas a new category is a decision. Removals are automatic, additions are declared.

## Commands

Run these from `docusaurus/`.

| Command | What it does |
|---|---|
| `npm start` | materialises, then starts the dev server |
| `npm run build` | materialises, then builds the public site |
| `npm run build-internal` | same, for the GitHub Enterprise target |
| `npm run materialize` | writes the generated tree from `content/` |
| `npm run verify` | fails if the generated tree is out of date, or was edited by hand |
| `npm run check` | the content diagnostics, without building anything — seconds, not minutes |

`build`, `build-internal` and `start` materialise first through `prebuild`/`prestart`, so there is nothing
extra to remember.

### Cutting a release

```bash
cd docusaurus
npx docs-overlay cut 11.15.0
```

`content/docs/next/` becomes `content/docs/11.15.0/`, and `next/` comes back empty — inheriting
everything, so `/next/` serves the new release until someone writes into it. `versions.json`,
`lastVersion` and the version dropdown all follow from the folders, so there is nothing else to update.

[`ADDING-A-VERSION.md`](../ADDING-A-VERSION.md) is the procedure in full: what to verify afterwards, the
three cases where `cut` refuses and what each means, what to do about a release whose documentation did not
change, and why `docusaurus docs:version` must never be run again.

## Where the content comes from

`content/docs/next/atomic/` and `content/docs/next/atomic-angular/` are a **mirror**: they are
regenerated from the `atomic` and `atomic-angular` repositories, and edits made here are overwritten.
The Mint documentation (`content/docs/*/mint/`, `index.md`, `changelog.md`) is authored here.

Two consequences of the mirror landing in `next/` rather than in the released version:

- Library documentation reaches the published site at the next release cut, not immediately.
- The sync copies unconditionally, so it recreates an override for every file it touches, including ones
  identical to what they would inherit. Run `npm run check` afterwards; a sync that is not followed by a
  prune re-inflates the repository quietly.

## Deployment

Unchanged. Both GitHub Pages workflows are `workflow_dispatch` only, and both run `npm ci` then the
matching build script, which materialises on the way. The URLs are unchanged by this migration: the
newest release at the site root, `/next/…` for the channel, `/11.13.0/…` for the older version.
