# Preview Internals

This page explains in detail how the document preview works in Mint: how it is triggered when a user clicks a result, how the iframe content is fetched and validated, how entity highlights are applied, and how it adapts to different screen sizes.

:::tip
For a higher-level overview of the Preview component and its sub-components (navbar, header, tabs, assistant), see [Preview](./preview.mdx).
:::

## Triggering the Preview

### Step 1 — User clicks an article

Each article card calls `SelectionService.setCurrentArticle(article)`. This method writes the article into `SelectionStore`, making it available as a signal across the application.

### Step 2 — SelectionStore drives visibility

`SearchAllComponent` computes `hasPreview()` directly from the store:

```typescript
readonly hasPreview = computed(() => this.selectionStore.id?.() !== undefined);
```

When `hasPreview()` becomes `true`, the right-hand panel becomes visible via conditional rendering and CSS animation classes.

### Step 3 — Preview panel renders

There is no Drawer component. The `<preview>` element is rendered directly in the search results template:

**Desktop (≥ 1024 px):**

```html
<!-- src/app2/pages/search/search-all.html -->
<preview
  [class]="cn(
    'absolute inset-0 size-full',
    hasPreview() && 'z-0 animate-slide-in-right',
    !hasPreview() && 'z-1 translate-x-full animate-slide-out-right opacity-0'
  )" />
```

The panel slides in from the right using CSS animation classes. When `hasPreview()` is `false`, the reverse animation plays and the element becomes invisible.

**Mobile / Tablet (< 1024 px):**

A `<sheet-previewer>` side sheet component is used instead:

```html
<sheet-previewer class="hidden md:block" />
```

The `SheetPreviewerComponent` uses a `<sheet>` (side sheet from `@sinequa/ui`). It adapts its content based on the breakpoint:
- **Mobile (< 768 px):** shows only `<preview-content>` with the article title in a `<sheet-header>`
- **Tablet (768 px–1023 px):** shows the full `<preview>` component inside the sheet

### Step 4 — PreviewComponent reads the article

`PreviewComponent` does **not** receive the article as an `@Input()`. It reads it directly from `SelectionStore`:

```typescript
// src/components/preview/preview.ts
protected readonly article = computed(() => {
  const article = this.selectionStore.article?.();
  if (article) {
    this.applicationService.setTitle(article.title || "Preview");
  }
  return article as Article;
});
```

## Closing the Preview

Closing the preview goes through `PreviewNavbarComponent`:

```typescript
// src/components/preview/preview-navbar/preview-navbar.ts
handleClose() {
  this.queryParamsStore.patch({ id: undefined }); // removes id from URL
  this.selectionStore.clear();                    // clears SelectionStore
  this.onClose.emit();
}
```

Clearing `SelectionStore` sets `selectionStore.id()` to `undefined`, which makes `hasPreview()` return `false` in `SearchAllComponent`, triggering the slide-out animation.

For the `SheetPreviewerComponent`, closure is handled by the sheet itself:

```typescript
handleChange(open: boolean) {
  this.sheetService.setOpen(open);
  if (!open) {
    setTimeout(() => this.selectionService.clearCurrentArticle(), 200); // waits for animation
  }
}
```

ESC key also closes the sheet via:

```typescript
// src/components/preview/preview.ts
this.eventManager.addEventListener(this.document.body, "keyup", (event: KeyboardEvent) => {
  if (event.key === "Escape") this.sheetService.setOpen(false);
});
```

## Auto-open from URL

If the URL contains an `id` parameter (e.g., `#/search/all?id=doc-42`), `fetchServerPage` automatically opens the preview for the matching record as soon as the first page loads:

```typescript
// src/config/fetch-server-page.ts
if (id) {
  result.records?.forEach(article => {
    if (article.id === id) selectionService.setCurrentArticle(article);
  });
}
```

This makes preview state **shareable via URL**. The `id` parameter is written to the URL by Effect 2 in `SearchAllComponent` whenever `queryParamsStore.id` is set.

## PreviewContentComponent — iframe Loading Pipeline

`PreviewContentComponent` (`src/components/preview/preview-content/preview-content.ts`) manages the document iframe. It runs two Angular resources in sequence:

### Resource 1 — Fetch PreviewData

```typescript
previewDataResource = rxResource({
  params: () => ({
    id: this.id() || this.selectionStore.id?.() || "",
    text: this.selectionStore.queryText?.() || "",
    previewHighlights: this.selectionStore.previewHighlights?.()?.highlights
  }),
  stream: ({ params: { id, text, previewHighlights } }) =>
    this.previewService.preview(id, { name: this.queryName, text }, previewHighlights)
});
```

`previewService.preview()` calls the Sinequa backend to retrieve the `PreviewData` object, which contains the `documentCachedContentUrl` — the URL of the cached HTML version of the document.

### Resource 2 — Validate the cached URL

Before displaying the iframe, a HEAD request verifies the cached content is actually accessible:

```typescript
previewValidationResource = resource({
  params: () => ({ url: this.previewUrl(), previewData: this.previewData() }),
  loader: async ({ params }) => {
    const response = await fetch(
      window.location.origin + params.previewData.documentCachedContentUrl,
      { method: "HEAD" }
    );
    return { isValid: response.status === 200 };
  }
});
```

If the fetch fails, `previewService.DOMContentLoaded.set(true)` is called to stop the loading indicator, and a "preview unavailable" message is shown.

### Template states

| State | Display |
|---|---|
| `isLoading()` on either resource | Spinning loader icon |
| Both resources have values and `previewUrl()` is defined | iframe + preview navigator + preview actions |
| No preview data or validation failed | "Preview unavailable" message |

### iframe Communication

Once the iframe is mounted, its `contentWindow` is registered with `PreviewService`:

```typescript
effect(() => {
  const iframeElement = this.iframe();
  if (iframeElement) this.previewService.setIframe(iframeElement.nativeElement.contentWindow);
});
```

The parent and iframe communicate via `postMessage`:
- **To iframe:** `previewService.sendMessage({ action: "select", id: "snippet_123", usePassageHighlighter: true })`
- **From iframe:** `window.addEventListener("message", ...)` — receives `current-page` events to track the currently visible page

## Advanced Search (Entity / Extract Navigation)

The `<advanced-search>` component is rendered directly inside `PreviewComponent` (not in a separate drawer):

```html
<!-- src/components/preview/preview.html -->
<advanced-search
  [class]="cn('max-w-(clamp(200px,350px,100%)) h-full overflow-y-auto border-foreground/18 bg-menu', extended() && 'border-l')"
  [article]="article()"
  previewStrategy="replace" />
```

The host grid switches between `grid-cols-[auto_0fr]` (collapsed, Advanced Search invisible) and `grid-cols-[1fr_.5fr]` (extended, Advanced Search visible) based on the `extended` signal.

The "Search in document" button in the navbar toggles this signal:

```typescript
toggleExtended(): void {
  this.extended.set(!this.extended());
}
```

The button is only shown when `isPrimary` is `true` (primary document conversion) and `showSearchButton` is enabled in the navbar config.

## Expanded Preview Dialog

When the `expandPreview` feature flag is enabled (`AppStore.general()?.features?.expandPreview`), the navbar shows an expand button. Clicking it opens `PreviewDialogComponent`:

```typescript
onExpand(): void {
  this.previewDialog()?.open(this.article() as Article);
}
```

`PreviewDialogComponent` (`src/components/preview/dialog/preview-dialog.ts`) is a full-screen modal dialog that renders the preview with its own set of tabs:

| Tab | Description |
|---|---|
| Chat | Chat with the document (assistant, `preview-chatwithdoc-assistant`) |
| Summary | AI summary of the document (`preview-summarize-assistant`) |
| Find | Advanced search / entity navigation |

It provides its own `PreviewService` instance (`providers: [PreviewService]`) to keep the dialog's iframe state independent from the inline preview.

## Entity Highlighting

When the preview renders a document's content, named entities (companies, people, places, amounts, etc.) are highlighted with distinct colors.

### Configuration

The highlights are configured in `src/config/highlight.config.ts` and provided via the `HIGHLIGHTS` token:

```typescript
// src/app2/app.config.ts
{ provide: HIGHLIGHTS, useValue: PREVIEW_HIGHLIGHTS }
```

Each entry defines a category name, a CSS class applied in the iframe, and a color for the navigation UI.

| Category | Color |
|---|---|
| `company` | Red (`#FF7675`) |
| `geo` | Blue (`#74B9FF`) |
| `person` | Teal (`#00ABB5`) |
| `money` | Green (`#85BB65`) |
| `entity12` | Gold (`#FFD700`) |
| `matchlocations` / `extractslocations` | Yellow |

### How it works

The highlights configuration is consumed by `PreviewService` and `PreviewNavigator`:
1. CSS rules are injected into the iframe to colorize each entity class
2. The `<preview-navigator>` overlay (displayed above the iframe) lists entity categories and allows jumping between occurrences

## Zoom

The zoom is applied to the preview body, and it does two things that cost wildly different amounts:

| what | cost |
| --- | --- |
| `transform: scale(f)` | compositor, independent of document size |
| `width: calc(99% / f)` | **reflows the whole document** — O(DOM) |

The width is divided by the factor so that the body still fills the panel once scaled. That is also what makes page sheets flow side by side when zoomed out (`.stl_` is `display: inline-block`, so a wider *layout* fits more per row) and what re-wraps text in unpaginated conversions. It is wanted behaviour, but it must not be paid on every step.

So `preview.js` splits them. A zoom step writes only the transform; the width is committed once the zoom settles (`ZOOM_SETTLE_MS`), which coalesces a burst of clicks into a single reflow. A `zoom-fit`, or a `select` about to locate a citation, commits immediately — the citation must be placed on the final layout.

### Fitting

`zoom-fit` derives its factor from the document's own overflow — `scrollWidth` against the panel width — rather than by measuring elements. `scrollWidth` has one trap that has to be handled: for an element it is a local, **pre-transform** metric, but on the `body` **in quirks mode** it is special-cased to the document's scroll width, which lives in viewport space and therefore already includes the transform. The converters emit no doctype, so quirks is the common case here, and the factor has to be divided out. When nothing overflows, `scrollWidth` merely reports the viewport back, which is the signal that the factor is 1.

This replaced an implementation that measured every `div, img, table` in the document, and it fixed two real defects rather than only being faster:

- it **mixed coordinate spaces** — the widest width was measured after the transform but used as an absolute factor, so the result was only correct when the current factor happened to be 1. Since the server writes a factor inline and this runs at `DOMContentLoaded`, "fit" routinely left the content overflowing: on a double-page PDF it produced 0.79 where 0.34 was needed, i.e. a horizontal scrollbar at *fit*.
- `Math.max(...array)` over ~113 000 arguments **throws** `RangeError: Maximum call stack size exceeded`. Because `zoomFit()` runs before the `requestAnimationFrame` chain that posts `ready`, the throw took `ready` with it: measured on the bench, a 137 657-element document never became ready at all, leaving the host's spinner up until its safety net. The same document is ready in 3.8 s now, and a 63 539-element one gained 0.9 s.

The cached factor is dropped on a panel resize, so a later `zoom-fit` is computed for the new width. The current zoom is deliberately left alone — re-fitting on resize would undo a zoom the reader chose.

Two consequences worth knowing:

- **The zoom is applied as an inline `transform`, not by updating `--factor`.** A custom property inherits, so changing it invalidates style for every element in the subtree. Measured on the bench: ~65 ms per step on a 63 000-element document through `--factor`, against ~1 ms as an inline transform. `--factor` therefore keeps whatever the server wrote inline — `preview.css` uses it for the *initial* scale only — and anything that needs the live factor reads it from JS (or, from outside, from the resolved transform matrix). `renderPassage()` sets each frame's `border-width` inline for the same reason.
- **Between a step and the commit, the body's visual width is no longer exactly the panel width**, so a slight re-settling is visible when the layout catches up. That is the deliberate trade: instant feedback on every step, one reflow per gesture.

:::tip
`node preview-lab/run-profile.mjs` measures all of this without instrumenting `preview.js`. The column to watch is `zoom avg` — the style and layout a single step forces — which should stay flat as DOM size grows.
:::

## Passage Navigation

When a search result with a selected passage is opened, `PreviewContentComponent` scrolls the iframe to the relevant passage:

1. `SelectionStore.previewHighlights()` provides the `snippetId`
2. On iframe load, `previewService.sendMessage({ action: "select", id: "snippet_X", usePassageHighlighter: true })` scrolls and highlights the passage

For **secondary conversions** (multi-conversion), passage highlighting is not possible, so the component falls back to page-level scrolling:

1. `previewService.passageOffset()` provides the passage offset in the original document
2. `queryService.getDocPage(id, offset, length)` resolves the page number for that offset
3. `previewService.sendMessage({ action: "select", id: "sq-page-start-N" })` scrolls to the page

### Passage frames (the blue box)

`usePassageHighlighter: true` makes `preview.js` draw a blue frame around the passage. The frame is **not** a single rectangle: one frame is drawn per contiguous block of the passage, so a passage that crosses a page break or a column break gets one frame per page / per column instead of one box spanning everything in between.

The implementation lives in `src/assets/preview.js`:

1. `getClientRects()` on every element carrying the passage id yields **one rect per line fragment** — that is what makes wrapping, columns and page breaks visible to the algorithm.
2. Each rect is converted to the overlay's **local** coordinate space with `(rect - layerRect) / factor`. This matters because `preview.css` puts `transform: scale(var(--factor))` on the body: the transform makes the body the containing block of its absolutely positioned descendants, so the overlay is positioned in pre-scale coordinates while `getBoundingClientRect()` reports post-scale viewport coordinates. The single division handles both the scroll offset and the scale. The origin is taken from `#sq-passage-layer` itself rather than from the body, so that any offset applied to the layer cancels out — `#sq-passage-layer` is an ordinary `div` child of the preview body, and rules aimed at page sheets can reach it (`body.bd > div:not(.ph, .phe) { margin: 24px }` used to shift the whole overlay by 24 px on every PdfToHtml conversion).
3. Rects are grouped into blocks: never across two page sheets, then by line (vertical overlap, small horizontal gap — the column gutter is what separates two columns) and by consecutive lines of the same column. A page sheet is the body-level ancestor of the fragment, **provided it is not inline**: unpaginated conversions put the passage `<span>`s directly under the body, split into several fragments because passages overlap each other and HTML cannot express overlapping ranges. Keying on those would forbid merging fragments of the very same paragraph and produce overlapping frames.
4. Two paragraphs of the same passage separated by a blank line are merged too, but only while the result stays mostly text (`MIN_MERGE_DENSITY`): one frame around two paragraphs reads better than two, whereas a run of one-line captions must not collapse into a single, mostly empty box. Beyond one blank line the gap is a structural break and is never crossed.
5. One `.sq-passage-box` per block is appended to `#sq-passage-layer`, a zero-sized anchor pinned to the body origin.

Because the overlay lives inside the scaled body, the frames follow scroll and zoom for free — a zoom step scales them along with the text, so nothing has to be recomputed while the zoom is still moving. They are recomputed once the zoom *settles* (the layout width changes then, which re-wraps text and changes how many sheets fit per row), and on resize, scroll, description toggling, any `load` event inside the content document, and once `document.fonts` is ready.

The `ResizeObserver` on the preview body is **not** the safety net it looks like: `preview.css` gives that body an explicit width and height, so its box never changes when the content grows. It reports a zoom or a panel resize, nothing else. Anything that reflows the content — a late image, a late font — has to be observed at its source, which is what the `load` and `fonts.ready` hooks are for.

#### Scrolling to the passage

`preview.js` does **not** use `scrollIntoView`. Neither of its two modes works here: `container: "all"` walks past the iframe and scrolls the host application back to the top (ES-31592), while `container: "nearest"` stops at the nearest scroll container — and `overflow: hidden` is enough to create one. The PdfToHtml family emits `.t { position: absolute; overflow: hidden }` on **every single word**, so the nearest scroll container of a citation is the word itself: it cannot scroll, it absorbs the request, and the document never moves. The blue frame is then drawn correctly, off-screen, where nobody sees it.

Instead, `scrollAnchorIntoView()` walks up from the anchor and scrolls each ancestor that is *genuinely* scrollable (computed `overflow` of `auto`/`scroll`/`overlay` **and** actual overflow — which keeps a plain-text pane working while skipping the ones that only clip), then centres the anchor in the preview viewport itself. Nothing outside the preview document is ever scrolled, so the ES-31592 regression cannot come back. Note that the converters emit no doctype: the content document is in **quirks mode**, where the scrolling element is `body`, not `documentElement`.

Scrolling once is not enough, because the document can still move afterwards. `PptxToHtml` emits `<img loading="lazy">` with **no width or height attribute**, so the intrinsic size of each slide bitmap *is* the layout: every image that arrives after the scroll pushes the text further down, by hundreds of pixels over a whole deck. The frames were recomputed but the scroll position was not, so the passage drifted out of view — and selecting the same citation again appeared to fix it, because the images were cached by then. A reflow therefore re-centres the passage as well, but only during a **settling window** of `PASSAGE_SETTLE_MS` after the select, and any `wheel`, `touchstart` or `keydown` ends that window immediately: the app owns the scroll only until the reader takes over. The scroll event itself is never allowed to re-anchor — it would fight the user, and recurse.

Two special cases:

- **AI page descriptions.** Multimodal conversions emit their generated full text in `.pn_page_visual_description` blocks, which are hidden by default (`--desc-display: none`). When the cited passage lives there, `preview.js` reveals the block, then frames the passage, and notifies the parent with a `description-visible` message so that the *sparkles* toggle in `<preview-actions>` reflects the new state.
- **Nothing measurable.** If no geometry can be obtained after a short retry loop (image-only conversion, for instance), the passage text is tinted with `.sq-highlighted` as a last resort.

:::tip
`preview-lab/` at the repository root is a dependency-free test bench for this feature: it loads the real `preview.js` / `preview.css`, drives them over `postMessage` like `PreviewService` does, and asserts the frame geometry across a matrix of widths and zoom levels. Run `node preview-lab/run-ci.mjs`.
:::

## Responsive Summary

| Screen size | Preview presentation | Opened by |
|---|---|---|
| Desktop (≥ 1024 px) | Inline right panel, 50% width, slide-in animation | `hasPreview()` CSS toggle |
| Tablet (768 px–1023 px) | Side sheet (full `<preview>`) from the right | `SheetPreviewerComponent` |
| Mobile (< 768 px) | Side sheet (title + `<preview-content>` only) from the right | `SheetPreviewerComponent` |
