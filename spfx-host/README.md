# SPFx host for Sinequa Mint

Glue that runs the Angular **mint** application (`spfx` build) inside a SharePoint Framework web part,
with **Azure AD** authentication via `AadHttpClient` / `AadTokenProvider`.

> These files are a **template** for a **separate** SPFx solution (generated by the Yeoman SharePoint
> generator). They are **not** compiled by mint's Angular build (they live outside `src/` and import the
> `@microsoft/sp-*` packages).

## SPFx mode (npm switch)

`@microsoft/sp-http` is **not** a declared dependency of mint. It is needed only by the `spfx` /
`spfx-production` builds, and only as a *type provider* (`import type` in
`src/config/spfx/spfx-context.ts`). Declared, it dragged 24 `@microsoft/*` packages into the lockfile
and made every `npm install` print `EBADENGINE` warnings under Node 24 — for every dev, including
those who never touch SPFx. It is therefore provisioned **on demand**:

| Script | Effect |
|---|---|
| `npm run spfx:enable` | installs `@microsoft/sp-http` with `--no-save` (node_modules only) + creates `proxy.conf.spfx.json` from `proxy.conf.spfx.template.json` when missing |
| `npm run spfx:disable` | removes it from node_modules |
| `npm run spfx:status` | reports the current mode — git cannot tell you, since nothing is committed |

- `npm run start:spfx` and `npm run build:spfx` call `spfx:enable` themselves: in practice you never
  have to think about it.
- **Nothing is written to `package.json` / `package-lock.json`.** The mode lives in `node_modules`
  only, and `scripts/spfx-mode.mjs` restores both files if npm rewrites them — so the mode can never
  be committed by mistake.
- A later `npm install` prunes the package again (extraneous by design) → re-run `spfx:enable`, or
  just use `start:spfx` / `build:spfx`.
- Without the mode enabled, an `spfx` build fails with
  `TS2307: Cannot find module '@microsoft/sp-http'`. That is expected, not a regression.
- `spfx:enable` replays, **in the same npm command**, the `@sinequa/agent` / `@sinequa/assistant`
  override that `postinstall` applies (also `--no-save`): any other `npm install --no-save` re-reifies
  the tree and would otherwise silently downgrade the agent lib to the version pinned in
  `package.json`.

## Run modes: DEV (mock) vs PROD

Key point: the real `AadHttpClient` / `AadTokenProvider` **only exist inside an actual SharePoint page**
(they come from `this.context.aadHttpClientFactory` in the web part). Without an SPFx host you cannot
mint a real AAD token. So "pointing at PROD" is **not** "`ng serve` against a prod backend": it is a
**change of run mode** (deploy the web part), not just a URL to change.

In **DEV**, `src/main.spfx.ts` detects the missing host context (`!__MINT_SPFX_CONTEXT__`) and, outside
production, **fabricates** a mocked context (`src/config/spfx-context.mock.ts`) that hits the Sinequa
auth playground.

| Aspect | DEV (mock) | PROD (real SharePoint) |
|---|---|---|
| AAD context | `createMockSpfxContext()` → playground | `MintWebPart.render()` → real `window.__MINT_SPFX_CONTEXT__` |
| Token | fake endpoint `/__mock/aad-token` | `login.microsoftonline.com` via the SPFx context |
| `proxy.conf.spfx.json` | proxy → `http://localhost:5173` (route `/__mock`) — git-ignored, generated from `proxy.conf.spfx.template.json` by `npm run spfx:enable` | **unused** (no `ng serve`; real cross-origin calls) |
| Backend | mock playground | real `backendUrl` (web part property pane) |
| `@sinequa/atomic` | published package + `/spfx` subpath | same (see *Packaging — production*) |
| `environment.production` | `false` (mock guard active) | `true` (no context → 500 page, **no** mock) |

⚠️ For a PROD build, make sure the `environment` in use has `production: true` — otherwise the
`main.spfx.ts` guard would stay active and mock instead of erroring when the host context is missing.
The `spfx-production` build configuration handles this (see step 1).

> Testing **locally against a real Sinequa backend** (without a SharePoint deployment) is a separate,
> trickier case: it would require a real AAD token outside an SPFx host. Not covered here.

> **No SPFx-only test environment.** Local SPFx development (`npm run start:spfx`, i.e.
> `--configuration spfx`) runs only against the mocked AAD context (`spfx-context.mock.ts`) and the
> Sinequa Auth Playground — a fake backend, not a real SharePoint host. There is no dedicated SPFx test
> backend.
>
> As a result, keep `src/environments/environment.ts` at its standard dev values — do **not** commit
> SPFx-test-specific tweaks there (e.g. hardcoding `app: "spfx"`). The `spfx` serve build does **not**
> replace `environment.ts`, and the mocked context (`createMockSpfxContext()`) supplies **only** the AAD
> auth (`aadTokenProvider`, `aadHttpClient`, `resourceUri`) — **not** `app` / `backendUrl`. So in DEV the
> `app` is taken straight from `environment.ts` (via `setGlobalConfig(environment)` in `main.spfx.ts`);
> a `app: "spfx"` tweak only changes which Sinequa app your local playground queries hit — a test-only
> concern. In **prod** none of this applies: `environment.ts` is replaced by
> `environment.spfx.production.ts` (`fileReplacements`) **and** the host web part injects
> `backendUrl` / `app` at runtime. Either way, SPFx-test edits to `environment.ts` are local-only and
> must be reverted before committing.

## Architecture

```
SharePoint page
└─ MintWebPart (BaseClientSideWebPart)         ← spfx-host/MintWebPart.ts
   ├─ getClient(resourceUri) ........ AadHttpClient (lib web-api → AAD)
   ├─ getTokenProvider() ............ AadTokenProvider (Angular interceptor → AAD)
   ├─ window.__MINT_SPFX_CONTEXT__ = { aadHttpClient, aadTokenProvider, resourceUri, backendUrl, app }
   └─ loadMintAssets(assetsBaseUrl) . injects styles.css + polyfills.js + main.js
      └─ main.js (mint spfx build) ← src/main.spfx.ts
         ├─ setGlobalConfig({ backendUrl, app })
         ├─ initializeAadHttpClient(aadHttpClient)   → lib web-api via AAD
         ├─ provide AAD_TOKEN_PROVIDER / AAD_RESOURCE_URI → aadAuthInterceptorFn interceptor
         └─ bootstrapApplication(AppComponent) on <app-root>
```

The web part **contains no UI**: it is only the bridge that provides the AAD context and loads the
bundle. The whole application stays in mint.

## Contents

| File | Role |
|---|---|
| `MintWebPart.ts` | Web part: gets the AAD context, publishes it on `window.__MINT_SPFX_CONTEXT__`, loads the bundle. |
| `load-mint-assets.ts` | Idempotent injection of `styles.css` + `polyfills.js` + `main.js`. |

Copy into `src/webparts/mint/` of the SPFx solution (and wire up the web part manifest).

## Prerequisites

1. **SPFx solution** generated (`yo @microsoft/sharepoint`), SPFx ≥ 1.20.
2. **Azure AD app registration** for the Sinequa API, with **admin consent** granted on the tenant.
3. **Sinequa** configured to accept Azure AD tokens (OAuth/AAD provider), with an audience matching the
   `resourceUri` requested by the web part.
4. **CORS**: the Sinequa server must allow the SharePoint origin (calls are **cross-origin**).

## ⚠️ Node version — two separate build environments

There are **two independent builds**, and Node's version only constrains one of them:

| Build | Tool | Node | Where |
|---|---|---|---|
| **mint bundle** (`ng build … --configuration spfx-production`) | Angular CLI | **24 OK** (Angular 20/22 supports it) | this repo (`mint-internal`) |
| **`.sppkg` packaging** (`gulp bundle --ship` + `gulp package-solution`) | SPFx toolchain (`@microsoft/sp-build-web`) | **Node 22 required** | the **separate** Yeoman SPFx solution |

- **Production is Node-agnostic.** At runtime everything runs in the browser inside a SharePoint page; the
  Node version plays no role. SPFx in production works fine.
- **The mint bundle builds on Node 24.** The `@microsoft/sp-*` packages are **dev-only type providers**
  (`src/config/spfx/spfx-context.ts` uses `import type`; `MintWebPart.ts` lives outside `src/` and is
  not compiled by `ng build`). They are never executed under Node, so their `EBADENGINE` warnings are
  cosmetic — and since they are no longer declared dependencies, the warnings only show up when you
  run `npm run spfx:enable` (see *SPFx mode*), never on a standard `npm install`. This matters because
  the Angular 22 branch *requires* Node 24.
- **Package the `.sppkg` on Node 22.** This is the one real requirement: the SPFx gulp toolchain genuinely
  breaks on Node 24, so the separate SPFx solution must be built on Node 22.14+ (LTS). It is an independent
  project from mint, so there is no conflict with mint's Node 24.

## Steps

### 1. Build the mint bundle (production `spfx` build)
```bash
cd mint-internal
npm run build:spfx     # = spfx:enable + ng build --configuration spfx-production
# → dist/sinequa-mint/ (styles.css, polyfills.js, main.js, chunk-*.js, assets/…)
```
Use the npm script rather than a bare `ng build`: it provisions the SPFx types first (see *SPFx mode*).
The `spfx-production` configuration enables optimization, sets `production: true`, and keeps
`outputHashing: "none"` so the asset names stay fixed (`main.js` / `polyfills.js` / `styles.css`),
which the host loader (`load-mint-assets.ts`) relies on. Use `--configuration spfx` only for the local
DEV (mock) build.

### 2. Host the assets
Publish the **contents** of `dist/sinequa-mint/` to a public URL (Office 365 CDN, SharePoint library,
Azure Storage…). That URL becomes `assetsBaseUrl`. Lazy chunks resolve relative to `main.js`, so
everything must be hosted **in the same place**.

### 3. Declare the API permission (AAD) in the SPFx solution
In `config/package-solution.json`:
```jsonc
"webApiPermissionRequests": [
  { "resource": "<name or App ID of the Sinequa AAD app>", "scope": "<scope, e.g. user_impersonation>" }
]
```
After deploying the `.sppkg`, approve the request in **SharePoint admin center → API access**.

### 4. Configure the web part (property pane)
| Property | Example | Note |
|---|---|---|
| `backendUrl` | `https://sinequa.contoso.com` | **Required** — see pitfalls below |
| `app` | `mint` | Sinequa app name |
| `resourceUri` | `api://sinequa-search/.default` | Must match the audience validated by Sinequa |
| `assetsBaseUrl` | `https://cdn.contoso.com/mint/` | Where the contents of `dist/sinequa-mint` are hosted |

## ⚠️ Pitfalls

- **`backendUrl` is required.** In SharePoint, `window.location.origin` is the SP site (not Sinequa) and
  there is no dev proxy. Without `backendUrl`, `api/v1/*` calls go to SharePoint. The web part provides
  it via the context; `main.spfx.ts` applies it before bootstrap.
- **Single instance** of the web part per page (one Angular app). `loadMintAssets` is idempotent but
  does not guard against two `<app-root>` elements.
- **CORS** on the Sinequa side for the SharePoint origin, otherwise `AadHttpClient` requests fail at
  preflight.
- **Font Awesome / assets**: if mint depends on it (see `src/index.html`), host `assets/` too and
  uncomment the matching line in `load-mint-assets.ts`.
- **Zoneless**: mint uses `provideZonelessChangeDetection` → no `zone.js`, fewer conflicts with the
  SharePoint page.

## Authentication — flow recap

`AadHttpClient` carries the AAD bearer on the lib web-api; the `aadAuthInterceptorFn` interceptor
carries it on direct Angular `HttpClient` calls. At bootstrap, `signIn()` → `login()` →
`getCsrfToken()` (a **200 with no token** = `null`, not an error) then, if there is no session, the
`tryAutoAuthentication()` probe on `api/v1/principal`: a **200** (thanks to the AAD bearer) = authenticated
without a login form.

## Packaging — production

Nothing SPFx-specific to publish. `@sinequa/atomic` (≥ 2.1.0) already ships the `/spfx` subpath
(`initializeAadHttpClient`, `AadHttpClientLike`) and declares `@microsoft/sp-http` as an **optional**
peer dependency, never bundled. Mint consumes the regular published package: no
`@sinequa/atomic-spfx` alias, no local `file:` build. The only prerequisite for a prod bundle is
`npm run build:spfx`, which enables the SPFx mode itself.
